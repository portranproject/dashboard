# 대시보드 설계도 — 관제 · 성능 (M10)

2026-11-09 · 상태: **초안** · 기준: 탐지 엔진 명세 27_ §7 '화면과 레코드'(`reference/detection/`), 저장 구조 `schema/SCHEMA.md` 5절(M8)

M10에서 처음 대시보드 2개(`realtime.json`·`evaluation.json`, mock 메시지 기준)를 지우고 이 설계대로 다시 만든다(관제 `monitoring.json` 완료, 성능 `performance.json`은 탐지 성과까지 완료 — 오버헤드는 형식이 정해진 뒤). 패널마다 "무슨 질문에 답하나 → 어떤 레코드로"를 먼저 정해, 저장 구조를 다시 고칠 일이 없게 한다.

## 0. 요약

| 항목 | 내용 |
|---|---|
| 대시보드 | **관제**(지금 무슨 일이 일어나나) · **성능**(탐지가 얼마나 잘 됐나) 2개 |
| 데이터 출처 선택 | 두 대시보드 맨 위에 **AWS / On-Premise** 선택. 같은 대시보드가 고른 출처의 데이터만 보여 준다(1절). **지금은 AWS만 받는다** — On-Premise는 나중에 선택지 하나를 더하는 것으로 끝나게 구조만 잡아 둔다 |
| 저장 구조 | M8 구조(`env` 태그 등)로 모두 그릴 수 있다. **바꿀 것 없음**(5절) |
| 지금 못 만드는 것 | 탐지율·오탐·탐지 지연·오버헤드 — 정답 기록과 평가 방식을 전체 파이프라인 완성 뒤 탐지 쪽과 정하기로 함(27_ §9). 자리만 잡아 둔다(3.2절) |

## 1. 데이터 출처 선택

테스트베드는 AWS(CU·DU 인스턴스 세트)와 On-Premise(연구실 실물 테스트베드) 두 곳이다(구성 그림은 `CLAUDE.md` 1.1절). 탐지 엔진 전송기가 붙이는 `X-Env` 헤더가 InfluxDB `env` 태그로 저장되고(M8), 이 태그로 출처를 가른다.

| 선택지(화면 이름) | `env` 값 | 어디서 오나 (27_ §3) | 지금 |
|---|---|---|---|
| **AWS** | `p4` | AWS 테스트베드 p4 CU 박스 (공인 IP `43.202.191.147` 고정) | **받는다** |
| **On-Premise** | `lab` | 연구실 실험 노트북 | 선택지만 있음 — 받는 것은 나중 (사용자 결정 11/09 — 우선 AWS만, 11/11 선택지 추가) |
| 재생 | `replay` | `replay`로 다시 보낸 녹화 — 시연 백업 | 쓴다 |
| 샘플 | `sample` | 탐지 쪽 시험 샘플 — 개발용 | 쓴다 |

- Grafana 변수 `source`(사용자 정의, 한 개만 선택). 값은 `AWS : p4, On-Premise : lab, 재생 : replay, 샘플 : sample`(D150·D158). On-Premise는 아직 데이터가 없어 고르면 빈 화면이다. 받기 시작하면 대시보드는 고칠 것이 없다.
- 모든 쿼리에 `r.env == "${source}"`를 건다 — 나중에 출처가 둘이 돼도 데이터가 섞이지 않는다.
- 대시보드를 출처마다 따로 만들지 않는다. 화면이 같으므로 변수 하나로 바꾼다(패널을 고칠 때 두 벌을 맞출 일이 없음).
- 헤더가 없을 때의 `unknown`은 선택지에 넣지 않는다.

**On-Premise를 더할 때 정할 것** (지금은 하지 않음)
1. 연구실 노트북이 AWS `/ingest`로 보내려면 연구실 공인 IP를 보안 그룹에 열어야 한다(탐지 쪽이 확인해 알려 주기로 함, 27_ §9 D2⑤). 고정 IP가 없으면 다른 방법(VPN 등)이 필요하다.
2. 단계 비교 재생의 `X-Env`가 `replay-kpm-only` 하나뿐이라, 두 출처의 기록을 모두 재생하면 섞인다. 그때는 `p4-kpm-only`·`lab-kpm-only`처럼 출처를 붙여 달라고 요청한다. AWS만 받는 지금은 `replay-kpm-only` = AWS 기록의 재생이라 문제없다.

## 2. 관제 대시보드

새로고침 5초. 변수: `source`(1절), `cell`(그 출처의 `kpm2` 셀 목록), `alert_id`(시간 범위 안의 경보 — 경보 목록에서 행을 누르면 바뀜).

### 2.1 배치

```
┌ 요약 ─────────────────────────────────────────────────────────────────┐
│ 열린 경보(공격·이상 유형·판정 보류) │ 최고 심각도 │ 수집 상태 │ 지금 세션 │
├ 상시 KPM2 — 셀 ${cell}, 3초 ───────────────────────────────────────────┤
│ 시도·성공·무응답 막대 + 경보 구간(영역) + 세션 시작·재시작(세로선) + gap  │
│ UE 컨텍스트 수(ext.UeCtxMax) 선 + 셀 한도 96 기준선 · RRC 연결 UE 수      │
├ 경보 목록 ────────────────────────────────────────────────────────────┤
│ 시작 │ 셀 │ 단계 │ 룰 │ 공격 이름 │ 종류 │ 심각도 │ UE 수 │ 대표 값 │ 상태 │
│ 룰·단계별 경보 수                                                        │
├ 경보 상세 — ${alert_id} ──────────────────────────────────────────────┤
│ 판정 정보: 룰·공격 이름·단계·종류·성립 조건·후보 공격·전제·값·설정값       │
│ 걸린 UE 표 (2~4단계)                                                     │
│ 근거 KPM2 그래프 (1단계, 100 ms)  /  근거 KPM1 타임라인 (2~4단계, UE별)    │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 패널

| 행 | 패널 | 답하는 질문 | 레코드 (measurement · 조건 · 필드) |
|---|---|---|---|
| 요약 | 열린 경보 수 | 지금 울리고 있는 경보가 몇 개인가 | `alert` → `alert_id`별 마지막 `event`가 `raise`·`update`인 것. `kind`·`rule`로 공격 / 이상 유형(`AN-`) / 판정 보류(`rep_key == "held_w"`)를 나눠 센다(27_ §5.5) |
| 요약 | 최고 심각도 | 열린 경보 중 가장 심각한 것 | 위 경보들의 `severity` 최대(`high` > `medium` > 그 밖) |
| 요약 | 수집 상태 | 데이터가 지금 들어오고 있나 | 마지막 `kpm2`·`alert`·`evidence` 시각에서 지난 시간. `kpm2`가 끊겼으면 상시 경로가 꺼졌거나 분석 엔진이 멈춘 것 |
| 요약 | 지금 세션 | 분석 엔진이 언제 다시 떴나 | 마지막 `hello`의 `session`·시각, 시간 범위 안 `f1_evt` 수 |
| 상시 KPM2 | 연결 시도·성공·무응답 | 셀에 무슨 일이 일어나고 있나 (1단계 공격은 시도·무응답이 함께 솟고 성공은 그대로) | `kpm2` 필드 `cc.RRC.ConnEstabAtt.total`·`cc.RRC.ConnEstabSucc.total`·`cc.RRC.ConnEstabFailCause.NoReply`, 3초 막대 |
| 상시 KPM2 | UE 컨텍스트 수 | 셀 자원이 고갈되고 있나 | `ext.UeCtxMax` 선 + 셀 한도 96 기준선(27_ §5.3 `high` 조건 = 90%) · `si.RRC.ConnMax`·`si.RRC.ConnMean` |
| 상시 KPM2 | (겹쳐 표시) | 경보가 언제 울렸나 | 주석: `alert` `raise`~`clear`/`end` 구간(영역), `hello`(세션 시작, 파랑)·`f1_evt`(DU·CU 재시작, 보라) 세로선 — 색과 토글을 나눈다(D157), `gap` 구간 '데이터 없음' |
| 경보 목록 | 경보 표 | 어떤 경보가 있었나 | `alert`를 `alert_id`로 묶어 한 행: 시작 = `raise`의 시각, 심각도 = 최대, UE 수 = 마지막 `ues_total`, 대표 값 = 마지막 `rep_value`(`rep_key`), 상태 = 열림 / 해제(`clear`) / 강제 종료(`end`·`reason`) / 상태 불명(4절). 공격 이름은 6절 대응표 |
| 경보 목록 | 룰·단계별 경보 수 | 어떤 공격이 많았나 | `alert` `event == "raise"`를 `rule`·`stage`로 셈 |
| 경보 상세 | 판정 정보 | 왜 이 경보가 났나 | `alert_id == ${alert_id}`의 `cond_json`·`candidates_json`(→ 이름)·`conditions_json`·`mode`·`branch`·`params_json`. `values_json`은 **마지막 것**(`update`가 덮어씀, 27_ §7) |
| 경보 상세 | 걸린 UE 표 (2~4단계) | 어느 단말이 걸렸나 | `raise`·`update`의 `ues_json`을 **모두 합침**(`update`에는 새로 걸린 UE만 옴). 열: `cell`·`du_ue_id`·`uid`·`s_tmsi`·`crnti`·`t_hit`·`cond`·`uncertain`·`values` |
| 경보 상세 | 근거 KPM2 그래프 (1단계) | 경보 직전·중에 셀 카운터가 어땠나 | `evidence` `raw_type == "kpm2"`, 100 ms 칸마다 `cc.*` 막대. `raise`의 `refs_json`(`a` 시도 창, `f` 무응답 창의 `seq` 범위)을 `evidence.seq`로 시각에 맞춰 강조. `gap`은 '데이터 없음' |
| 경보 상세 | 근거 KPM1 타임라인 (2~4단계) | 걸린 단말이 어떤 메시지를 어떤 순서로 주고받았나 | `evidence` `raw_type == "ue_evt"`를 UE(`uid`)별로 시각 순. 열: 시각·UE·방향(↑ `UL` / ↓ `DL`)·`proto`(색)·`msg`·`raw_json`의 `f`. 표로 시작하고, 흐름을 한눈에 보는 상태 타임라인(UE마다 한 줄)을 위에 둔다 |

## 3. 성능 대시보드

변수: `source`(1절), `cell`, `kpm_only`(단계 비교 대상, 기본 `replay-kpm-only`), 시간 범위(실험 구간, 기본 최근 24시간). 새로고침 1분.

```
┌ 탐지 결과 — 고른 시간 범위에 시작한 경보 ───────────────────────────────┐
│ 경보 수 — 종류별(공격·이상 유형·판정 보류) │ 단계 비교 요약(1~4단계·1단계만·못 잡은 경보) │
│ 단계 비교 — 룰별 경보 수(막대 두 개)        │ 경보 길이 분포(초)                          │
│ 룰 × 단계 × 종류 표(경보 수·high까지·해제·강제 종료·끝이 안 옴·평균·최대 길이)              │
├ 경보·입력 품질 ─────────────────────────────────────────────────────────┤
│ 경보가 어떻게 끝났나(해제·강제 종료 사유 3개·끝이 안 옴) │ 근거 손실(보낸·버린·손실률)        │
│ 입력 끊김 gap(수·빠진 시간) │ 상시 KPM2 칸 채움(전체·일부 없음·비율) │ 일부만 측정된 지표     │
├ 파이프라인 완성 뒤 채울 것 ─────────────────────────────────────────────┤
│ 탐지율·오탐·탐지 지연·수집 오버헤드 (자리만, 글)                                         │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.1 만든 것 — 경보 레코드만으로 (`performance.json`, D161)

| 패널 | 답하는 질문 | 레코드 |
|---|---|---|
| 경보 수 — 룰 × 단계 × 종류 | 실험 동안 무엇이 몇 번 울렸나 | `alert` `raise`. 공격 경보만 '탐지 1건'으로 세고, 판정 보류·이상 유형은 따로 센다(27_ §5.5 제안) |
| **단계 비교 — 1~4단계 vs 1단계만** | 표준 KPM(1단계)만으로는 못 잡고 UE 메시지(2~4단계)로 잡은 것이 무엇인가 — **프로젝트 핵심 주장** | 같은 기록을 원본(`p4`)과 1단계만(`replay-kpm-only`, 27_ §3)으로 재생한 `alert`를 룰별로 나란히. 1단계만에는 2~4단계 경보가 없어야 하고, 그 차이가 "eKPM이 더 잡은 것". On-Premise를 더하면 출처별 재생 이름이 필요하다(1절) |
| 경보 길이 분포 | 경보가 얼마나 오래 이어졌나 | `alert` `clear`·`end`의 `duration_ms` |
| 근거 손실 · 끝이 안 온 경보 | 근거가 빠지거나 끝을 모르는 경보가 있었나 | `evidence_sent`·`evidence_dropped` 합, `clear`·`end`가 오지 않은 경보 수(끝난 실험이라 근거로 상태 불명을 가리지 않고 '끝이 안 옴'으로 센다) |
| 입력 품질 | 탐지 엔진이 받은 입력이 온전했나 | `gap` 수·길이, `kpm2`의 `n`이 칸을 다 못 채운 비율, `partial_json`에 든 지표 |

### 3.2 파이프라인 완성 뒤 채울 것 (27_ §9)

| 패널 | 필요한 것 | 지금 |
|---|---|---|
| 탐지율 · 오탐 | 정답 기록(공격 구간)과 경보를 맞추는 규칙 — R1 `eval`·R2 `eval_run` | 탐지 쪽과 함께 정하기로 미룸. 화면에 "파이프라인 완성 뒤" 자리만 둔다 |
| 탐지 지연 | 경보별 지연 — R3 | 위와 같음 |
| 수집 오버헤드 | 측정 주체·형식 — R5 | 탐지 쪽 협의 중. 옛 `overhead` 메시지는 그대로 받음 |

처음 evaluator(`eval_result`, mock 메시지 기준)는 M10에서 지웠다. 평가 방식이 정해지면 새로 만든다.

## 4. 데이터가 없거나 불완전할 때

| 경우 | 화면 처리 | 근거 |
|---|---|---|
| `null`·키 없음 | 0이 아니라 **'데이터 없음'**(선을 잇지 않음). 저장 단계에서 `null` 필드는 빠져 있다 | 27_ §2.4 |
| 레코드 자체가 안 옴 (상시 KPM2 점 사이가 6초 = 3초 묶음 2칸보다 김) | 선을 끊어 빈칸으로 둔다(Grafana `insertNulls`). 이으면 받지 않은 구간에 값이 서서히 변한 것처럼 보인다 | D156 |
| `kpm2`의 `n`이 칸을 다 못 채움 (`n < agg_ms / period_ms`) | 그 칸에 '일부 없음' 표시 | 27_ §4.1 |
| `gap` | 그 구간을 '데이터 없음' 영역으로 | 27_ §6.4 |
| 열린 경보에 레코드가 끊김 | 마지막 레코드(경보·근거) 뒤 **1단계 15초, 2~4단계 90초** 동안 아무것도 없으면 '상태 불명' | 27_ §7 |
| 재수립·재개 카운터 | 분석 엔진이 아직 못 세서 `null`로 옴 → 패널에 '측정 안 됨' | 27_ §4.1 |
| 고른 출처·시간 범위에 데이터가 없음 | "이 출처·구간의 데이터가 없습니다" 문구(빈 그래프 대신) | 1절 |

## 5. 저장 구조(M8)와 맞는지

모든 패널을 지금 저장 구조로 그릴 수 있다. 바꿀 것은 없다.

| 필요한 것 | 저장 위치 |
|---|---|
| 출처 거르기 | 모든 measurement의 `env` 태그 |
| 경보 하나의 레코드 묶기 | `alert`·`evidence`·`gap`의 `alert_id` 태그 |
| 경보 상태·심각도·UE 수·대표 값 | `alert`의 `event` 태그, `severity`·`ues_total`·`rep_value`·`rep_key` 필드 |
| 판정 정보·걸린 UE | `alert`의 `*_json` 필드 (Grafana에서 JSON으로 펼침) |
| 근거 그래프·타임라인 | `evidence`의 `raw_type`·`cell` 태그, `cc.*`·`msg`·`dir`·`proto`·`uid`·`seq`·`raw_json` 필드 |
| 상시 KPM2 | `kpm2`의 `cell`·`session` 태그, `cc.*`·`si.*`·`ext.*`·`n` 필드 |
| 세션·재시작 표시 | `hello`·`f1_evt` |

## 6. 룰 ID → 공격 이름

경보 레코드에는 공격 이름이 없고 ID(`rule`·`candidates`)만 온다. 이름은 대시보드가 27_ §5.3 대응표(룰 13개 + 후보 경로 ID)로 붙인다(11/02 합의).

- 대응표를 파일 하나(예: `grafana/rule-names.json`)에 두고, 대시보드 JSON의 값 매핑(value mapping)을 거기서 만든다. 테스트로 둘이 같은지 확인한다(대시보드마다 손으로 고치면 어긋남).
- 표기는 27_ 그대로(예: `L3-20` → "#20 Blind DoS (S-TMSI 재사용)", `AN-02` → "4단계 이상 유형 — 식별 요청 증가").
