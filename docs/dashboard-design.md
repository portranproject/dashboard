## 1. 데이터 출처 선택

테스트베드는 AWS(CU·DU 인스턴스 세트)와 On-Premise(우리 실물 장비 테스트베드) 두 곳이다(구성 그림은 `CLAUDE.md` 1.1절). 탐지 엔진 전송기가 붙이는 `X-Env` 헤더가 InfluxDB `env` 태그로 저장되고(M8), 이 태그로 출처를 가른다.

| 선택지(화면 이름) | `env` 값 | 어디서 오나 (27_ §3) | 지금 |
|---|---|---|---|
| **AWS** | `aws` | AWS 테스트베드 p4 CU 박스 (공인 IP `43.202.191.147` 고정) | **받는다** (11/20부터 `aws` — 탐지 쪽 변경) |
| **On-Premise** | `on-premise` | 우리 실물 장비 테스트베드 — 공인 IP는 보안 그룹에 열어 둠 | **받는다** (11/20, D213) |
| ~~AWS (이전 p4)~~ | `p4` | 11/13~11/20에 `p4`로 받은 AWS 실측 | 11/27에 선택지에서 없앰(사용자 요청, D223 — 데이터는 InfluxDB에 남음) |
| 재생 | `replay` | `replay`로 다시 보낸 녹화·탐지 쪽 시험 샘플 — 시연 백업·개발용 | 쓴다 |
| ~~샘플~~ | `sample` | 탐지 쪽 시험 샘플 — 개발용 | 11/27에 선택지에서 없앰(사용자 요청, D224 — 샘플은 `replay`로 넣어 '재생'에서 봄, 데이터는 InfluxDB에 남음) |

- Grafana 변수 `source`(사용자 정의, 한 개만 선택). 값은 `AWS : aws, On-Premise : on-premise, 재생 : replay`(D150·D158·D213·D223·D224).
- 모든 쿼리에 `r.env == "${source}"`를 건다 — 나중에 출처가 둘이 돼도 데이터가 섞이지 않는다.
- 대시보드를 출처마다 따로 만들지 않는다. 화면이 같으므로 변수 하나로 바꾼다(패널을 고칠 때 두 벌을 맞출 일이 없음).
- 헤더가 없을 때의 `unknown`은 선택지에 넣지 않는다.

**On-Premise를 더할 때 정할 것** (11/20 해결)
1. ~~On-Premise 장비가 AWS `/ingest`로 보내려면 공인 IP를 보안 그룹에 열어야 한다~~ — 연구실이 아니라 우리 장비에서 보내고, 그 IP는 열어 둠(사용자 11/20).
2. ~~단계 비교 재생의 `X-Env`에 출처 붙이기~~ — 단계 비교를 대시보드에서 없앴다(11/13, 3절).

## 2. 관제 대시보드

새로고침 5초 — 새로고침은 진행 중인 쿼리를 취소하므로 7일 범위도 쿼리마다 5초 안이어야 한다(`grafana/query_timing.py`로 잼, D202). 변수: `source`(1절), `cell`(그 출처의 `kpm2` 셀 목록), `alert_id`(시간 범위 안의 경보 — 경보 목록에서 행을 누르면 바뀜, 처음엔 가장 최근 경보). `alert_id`는 위쪽 칸을 숨긴다(D189).

### 2.1 배치

줄·패널 제목은 짧게 한다(11/16 사용자 요청): 줄은 탐지 결과 · KPM · 경보 목록 · 경보 상세, 근거 패널은 근거 KPM · UE_EVENT — UE별 메시지 흐름 · UE_EVENT — 메시지 흐름 상세. 셀·3초 묶음·셀 한도는 패널 설명(ⓘ)에 둔다.

```
┌ 탐지 결과 (고른 시간 범위에 시작한 경보, 11/16 요약 줄 대신 성능에서 옮김) ┐
│ 공격별 경보 수(막대)          │ 경보 길이 분포(초)                        │
│ 공격별 경보 결과 표                                                       │
├ KPM (상시 KPM2 — 셀 ${cell}, 3초) ──────────────────────────────┤
│ 시도·성공·무응답 막대 + 경보 구간(영역) + 세션 시작·재시작(세로선) + gap  │
│ UE 컨텍스트 수(ext.UeCtxMax) 선 + 셀 한도 96 기준선 · RRC 연결 UE 수      │
├ 경보 목록 ────────────────────────────────────────────────────────────┤
│ 시작 │ 셀 │ 룰 │ 공격 이름 │ 종류 │ 심각도 │ UE 수 │ 대표 값 │ 상태 │ 길이 │
├ 경보 상세 — ${alert_id} ──────────────────────────────────────────────┤
│ 판정 정보: 룰·공격 이름·종류·성립 조건·후보 공격·전제·값·설정값            │
│ 걸린 UE 표                                                               │
│ 근거 KPM2 그래프 (100 ms)  /  근거 KPM1 타임라인 (UE별)                   │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 패널

화면에는 단계(1~4)를 표시하지 않는다(11/13 사용자 결정 — 경보 목록·판정 요약의 단계 열과 경보 상세 제목의 '(1단계)'·'(2~4단계)'를 뺌). 아래 표의 괄호는 어떤 경보에서 나오는지 설명이다. 공격 이름은 짧은 이름(6절 대응표의 '#번호'·괄호 설명을 뺀 것).

| 행 | 패널 | 답하는 질문 | 레코드 (measurement · 조건 · 필드) |
|---|---|---|---|
| 탐지 결과 | 공격별 경보 수 · 공격별 경보 결과, 경보 길이 분포 (종류별 경보 수는 11/16에 없앰) | 고른 시간 범위에 무엇이 몇 번 울렸나 | 3.1절과 같은 계산(관제로 옮김, 11/16). 이전의 요약 줄(열린 경보·최고 심각도·수집 상태·지금 세션)은 없앴다 — 수집 멈춤은 Slack 알림(9.3) |
| 상시 KPM2 | 연결 시도·성공·무응답 | 셀에 무슨 일이 일어나고 있나 (1단계 공격은 시도·무응답이 함께 솟고 성공은 그대로) | `kpm2` 필드 `cc.RRC.ConnEstabAtt.total`·`cc.RRC.ConnEstabSucc.total`·`cc.RRC.ConnEstabFailCause.NoReply`, 3초 막대. 긴 시간 범위는 3초 배수 구간의 합(막대가 자기 구간을 덮음, D202) |
| 상시 KPM2 | UE 컨텍스트 수 | 셀 자원이 고갈되고 있나 | `ext.UeCtxMax` 선 + 셀 한도 96 기준선(27_ §5.3 `high` 조건 = 90%) · `si.RRC.ConnMax`·`si.RRC.ConnMean`. 긴 시간 범위는 3초 배수 구간의 최대(평균 선은 구간 평균, D202) |
| 상시 KPM2 | (겹쳐 표시) | 경보가 언제 울렸나 | 경보 구간 = `alert` `raise`~`clear`/`end`를 패널의 경보 계열(refId B)로 칠한 연한 주황 영역 — 영역 어디에 마우스를 대도 툴팁에 경보 종류·공격 이름·셀·상태·심각도(D204). 주석으로 칠하면 새로고침마다 깜빡여서 계열로 바꿈(D209 — 쿼리가 200 ms를 넘으면 Grafana가 로딩 중 빈 결과를 먼저 넘겨 주석이 잠깐 지워짐). kpm2가 없는 출처에서는 'No data' 대신 경보 영역만 보임. 주석: `hello`(세션 시작, 파랑)·`f1_evt`(DU·CU 재시작, 보라) 세로선 — 색을 나눈다(D157), `gap` 구간 '데이터 없음', '칸 일부 없음'(`n` < 3000 ÷ 그 세션의 `hello.period_ms` — 100 ms면 30, 1,000 ms면 3, `hello`가 없으면 100 ms로 봄, D214. 긴 범위는 세션·셀마다 구간으로 합침, D202). 주석은 늘 켜 두고 위쪽 토글은 숨긴다(D189) |
| 경보 목록 | 경보 표 | 어떤 경보가 있었나 | 셀 변수로 거름(11/25). `alert`를 `alert_id`로 묶어 한 행(룰 ID 열은 없애고 공격 이름으로만, 11/20): 시작 = `raise`의 시각, 심각도 = 최대, UE 수 = 마지막 `ues_total`, 대표 값 = 마지막 `rep_value`(`rep_key`, `ratio`는 % 정수 — 0.5714 → 57%, D203), 상태 = 열림 / 해제(`clear`) / 강제 종료(`end`·`reason`) / 상태 불명(4절). 공격 이름은 6절 대응표 |
| 경보 상세 | 판정 정보 | 왜 이 경보가 났나 | `alert_id == ${alert_id}`의 `cond_json`·`candidates_json`(→ 이름)·`conditions_json`·`params_json`(판정 요약의 모드·갈래 열은 없앴다 — 11/16 D193, 11/18 D203). `values_json`은 **마지막 것**(`update`가 덮어씀, 27_ §7). 키는 화면 이름으로 바꿔 보인다(7절, 11/25) |
| 경보 상세 | 걸린 UE 표 (UE 메시지 경보) | 어느 단말이 걸렸나 | `raise`·`update`의 `ues_json`을 **모두 합침**(`update`에는 새로 걸린 UE만 옴). 열: UE = `cell`-`uid`(D203 — `du_ue_id`는 InfluxDB `ue` 태그·원본에 남음)·`s_tmsi`·`crnti`·`t_hit`·`cond`·`peers`('피해자 연결' — Blind DoS에서만, 같은 S-TMSI를 원래 쓰던 단말의 연결, 화면에서 셀-uid)·`values`. 전제(`conditions`) 열과 판정 요약의 갈래(`branch`) 열은 없앴다(11/16, D193). 관측 오류(`uncertain`)·근거(`evidence`) 열도 없앴다(11/20, D210 — 값은 InfluxDB·원본에 남음) |
| 경보 상세 | 근거 KPM2 그래프 (셀 지표 경보) | 경보 직전·중에 셀 카운터가 어땠나 | `evidence` `raw_type == "kpm2"`, 100 ms 칸마다 `cc.*` 막대. `raise`의 `refs_json`(`a` 시도 창, `f` 무응답 창의 `seq` 범위)을 `evidence.seq`로 시각에 맞춰 강조. `gap`은 '데이터 없음' |
| 경보 상세 | 근거 KPM1 타임라인 (UE 메시지 경보) | 걸린 단말이 어떤 메시지를 어떤 순서로 주고받았나 | `evidence` `raw_type == "ue_evt"`를 UE별로 시각 순(UE = `cell`-`uid`, D203). 열: 시각·UE·방향(↑ `UL` / ↓ `DL`)·`proto`(색)·`msg`·`raw_json`의 `f`. 표로 시작하고, 흐름을 한눈에 보는 상태 타임라인(UE마다 한 줄)을 위에 둔다 |

### 3.3 CU 자원 — 수집 오버헤드 (M11)

eBPF는 늘 켜 두므로(사용자 결정 11/11) 켬·끔 비교가 아니라 **CU 자원 사용률의 추이**를 보고, 그 가운데 분석 엔진(계측기) 몫을 가른다. CU에 분석 엔진과 탐지 엔진을 함께 두므로(11/13) 노드 값에는 둘과 전송기·CU 프로그램이 모두 들어 있다. 레코드는 `overhead`(`schema/SCHEMA.md` 6절).

| 패널 | 답하는 질문 | 계산 |
|---|---|---|
| 노드 | 지금도 오나, CU 박스 크기는 | 늘 CU(`node_id`는 분석 엔진 실행 때 붙인 이름이라 쓰지 않음, D215). 마지막 `cpu_count`·`mem_total_bytes`, 마지막 구간 뒤 지난 시간(30초 넘으면 빨강) |
| CPU/메모리 평균 사용률 (11/20 전 '고른 시간 범위 요약') | 고른 시간 범위 동안 CU가 얼마나 바빴나, 그 가운데 분석 엔진 몫은(발표에서 한 줄로 말할 숫자) | 모두 평균(11/20 사용자 요청 — 최대는 3초 한 칸의 순간값이라 대표 값이 못 되고 시간 그래프에 보임): CPU % = `node_busy_cores` / `cpu_count`, 메모리 % = `used` / `total`, 분석 엔진 CPU % = `process_cores` / `cpu_count`(11/20 전에는 코어 수 — `0.000 코어`로 보여 바꿈), 분석 엔진 메모리 = `process_rss_bytes`. 순서는 전체 둘 → 분석 엔진 둘. 노드 칸과 글자 크기를 고정값으로 맞춤(자동이면 요약 칸 숫자가 훨씬 컸음) |
| CPU 사용률(전체) | 노드 CPU가 언제 올랐나 | `node_busy_cores` / `cpu_count` × 100. 시간 그래프는 모두 긴 시간 범위에서 3초 배수 구간의 평균(필드를 먼저 묶고 계산, D202). 노드·세션으로 나누지 않고 한 계열(D215) |
| CPU 사용률(분석 엔진) | 그 가운데 분석 엔진 몫은 얼마인가 | `process_cores` / `cpu_count` × 100 — 전체와 같은 기준(노드 CPU 전체의 %). 커널 안 eBPF 프로그램 시간은 이벤트를 일으킨 CU 스레드 쪽(전체)에 잡힌다. 11/20 전 'CPU 내역'(분석 엔진 + 그 밖 쌓기, 점선 코어 수)을 바꿈(사용자 요청) |
| 메모리 사용량(전체) · (분석 엔진) | 메모리가 새는가, 분석 엔진이 얼마나 쓰나 | 노드 `used`, 분석 엔진 RSS. 점선(전체 메모리)·'그 밖' 쌓기는 없앰(11/20 사용자 요청) — 전체 메모리는 '노드' 칸 |
| F1·N2 SCTP 트래픽 · 패킷 (범례 'F1 Ingress (DU → CU)'·'N2 Egress (CU → AMF)' — 필드 이름과 같은 영어, 11/20 전 들어옴·나감. NIC 이름은 툴팁에만) | 시그널링이 얼마나 오가나(부하) | `overhead_link`의 `wire_bytes`(바이트/초)·`sctp_packets`(패킷/초) 구간 증가분 ÷ 구간 길이(3초 평균, 긴 범위는 증가분의 구간 평균 ÷ 3초). Ingress(CU로 들어옴)는 위, Egress(CU에서 나감)는 아래. **SCTP 패킷만 센다**(F1AP·NGAP — F1-U 사용자 데이터 GTP-U는 빠짐, 탐지 쪽 11/13). 공격 때 시그널링이 몰리는 모양은 패킷 수에서 더 잘 보인다 |
| CPU 사용률 · RRC 연결 시도 (11/16 전 '부하와 함께') | 공격으로 연결 시도가 몰릴 때 CPU가 얼마나 오르나 | 왼쪽 축 CPU %, 오른쪽 축 상시 KPM2 RRC 연결 시도(고른 셀 합, 3초 칸 — 오버헤드와 같은 칸, 긴 범위는 같은 구간의 CPU 평균·연결 시도 합) |

### 3.4 수집 지연 (11/20, D211)

레코드가 대시보드 서버(collector)에 도착해 저장되기까지 걸린 시간. collector가 `/ingest`로 받은 줄마다 받은 시각 − 데이터 시각을 `ingest_delay`에 쓴다(CLAUDE.md 6절).

| 패널 | 답하는 질문 | 계산 |
|---|---|---|
| 수집 지연 백분위 (표) | 공격·지표가 얼마 만에 대시보드에 오나(발표에서 말할 숫자) | 한 행 = 종류 하나 — 'KPM 지연'(상시 KPM2, 칸 끝 기준), '경보 지연'(판정 시각 기준, raise·update·clear·end). 열: p50·p95·p99·개수(경보는 개수가 적어 p99가 맨 위 값에 가깝다). 고른 범위 전체를 정렬해 순위 int((n − 1) × q)로 고른다(정확값) |
| 수집 지연 추이 | 지연이 어떻게 변하나(추세) | 그래프 구간마다 그 안에 도착한 레코드 지연의 평균 — 'KPM 지연'(상시 KPM2, 파란 선)·'경보 지연'(주황 선 — 경보가 드물어 경보가 온 구간끼리 이음). 백분위의 평균이 아니다. 전송기 재시도(1~60초)·서버 지연 때 올라간다 |

- 화면에 보이기까지는 여기에 관제 새로고침 대기(최대 5초)와 쿼리 시간(0.5초 이하)이 더해진다 — 레코드마다 재는 값이 아니라 설명에 적는다.
- 데이터 시각은 분석 엔진 노드의 시계, 받은 시각은 대시보드 서버의 시계다. 둘이 어긋나면 그만큼 틀린다(열린 항목 Q8).

- 노드 변수는 두지 않았다(`node_id`는 `cu` 하나). 노드가 늘면 시간 그래프는 노드마다 계열이 생기고, 요약 숫자는 노드를 합쳐 계산한다 — 그때 노드 변수를 더한다.
- 프로세스별로 쌓으려면(Beszel의 컨테이너별 그래프처럼) 탐지 엔진·전송기도 따로 재야 한다. 지금 형식은 계측기 하나만 따로 잰다(`process_scope: self`).

## 4. 데이터가 없거나 불완전할 때

| 경우 | 화면 처리 | 근거 |
|---|---|---|
| `null`·키 없음 | 0이 아니라 **'데이터 없음'**(선을 잇지 않음). 저장 단계에서 `null` 필드는 빠져 있다 | 27_ §2.4 |
| 레코드 자체가 안 옴 (상시 KPM2·overhead가 없는 구간) | 선을 끊어 빈칸으로 둔다 — 쿼리가 빈 구간을 null 행으로 남긴다(`createEmpty: true`, 1시간 화면이면 3초 칸 하나만 빠져도 끊김). 이으면 받지 않은 구간에 값이 서서히 변한 것처럼 보인다 | D156 → D202 |
| `kpm2`의 `n`이 칸을 다 못 채움 (`n < agg_ms / period_ms`) | 그 칸에 '일부 없음' 표시. 긴 범위는 구간마다 하나(칸 수·가장 적은 n) | 27_ §4.1, D202 |
| `gap` | 그 구간을 '데이터 없음' 영역으로 | 27_ §6.4 |
| 열린 경보에 레코드가 끊김 | 마지막 레코드(경보·근거) 뒤 **1단계 15초, 2~4단계 90초** 동안 아무것도 없으면 '상태 불명' | 27_ §7 |
| 재수립·재개 카운터 | 분석 엔진이 아직 못 세서 `null`로 옴 → 패널에 '측정 안 됨' | 27_ §4.1 |
| 고른 출처·시간 범위에 데이터가 없음 | "이 출처·구간의 데이터가 없습니다" 문구(빈 그래프 대신) | 1절 |

## 6. 룰 ID → 공격 이름

경보 레코드에는 공격 이름이 없고 ID(`rule`·`candidates`)만 온다. 이름은 대시보드가 27_ §5.3 대응표(룰 13개 + 후보 경로 ID)로 붙인다(11/02 합의).

- 탐지 쪽 요청(11/27, D220): `L3-24`·`L3-14` 공격 경보(`kind` `attack`)는 화면 종류를 **이상 유형**으로 보인다(`rule-names.json` `shown_as_anomaly` — 경보 목록·판정 요약·탐지 결과·경보 툴팁. Slack은 11/27부터 이상 유형도 알려 제목만 🔶 이상 유형으로 바뀜, D222). 같은 룰의 판정 보류 경보는 그대로 판정 보류. `AN-02`(이름 '상향 IMSI 노출')의 후보 `L3-25-OV`(상향 IMSI 추출)는 이름이 겹쳐 후보 공격 표·판정 근거 값에서 뺀다(`hidden_candidates`). 레코드·InfluxDB·녹화는 그대로다.
- 대응표를 파일 하나(예: `grafana/rule-names.json`)에 두고, 대시보드 JSON의 값 매핑(value mapping)을 거기서 만든다. 테스트로 둘이 같은지 확인한다(대시보드마다 손으로 고치면 어긋남).
- 표기는 27_ 그대로(예: `L3-20` → "#20 Blind DoS (S-TMSI 재사용)", `AN-02` → "4단계 이상 유형 — 식별 요청 증가").

### 6.1 판정 근거 키 → 화면 이름 (11/25)

판정 근거 값(`cond`·`conditions`·`values`·`params`·`refs`)과 경보 목록 대표 값의 키는 탐지 쪽 35_ 분석표(`reference/detection/35_…xlsx`)의 '바꿀 값'(줄임말 없는 이름)으로 보인다. 대응표는 `grafana/evidence-key-names.json`(룰 → 항목 → 키 → 이름).

- **화면에서만 바꾼다.** 레코드 형식(27_)·InfluxDB·녹화는 원래 키 그대로라, 지난 데이터도 같은 이름으로 보이고 탐지 엔진·collector를 고치지 않는다. 탐지 쪽이 키를 바꿔 보내면 판정 근거 값 표는 그대로 따라가지만, 대표 값(collector의 룰별 대표 키)·지난 데이터와 어긋난다.
- 같은 키라도 룰·항목마다 이름이 다르다(`unsolicited`는 L3-24·L3-14·L3-06마다, L3-20 `concurrent`는 성립 조건과 관측값이 다름). 그래서 Flux에서 룰·필드로 갈라 JSON 문자열의 `"키":`(객체)·`"키"`(배열 원소)를 바꾼다 — 따옴표까지 맞춰 `C2`가 `C2a`를 건드리지 않는다.
- 대응표에 없는 키는 원래 키로 보인다(목록은 대응표의 `_이름_없음`). 후보 룰 ID는 바꾸지 않는다(후보 공격 표가 이름을 붙임).
